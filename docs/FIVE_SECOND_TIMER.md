# Five-second timer

The **5-Second Timer** is a separate application with an immutable physical 2×2 print. Countdown defaults to 30:00; Stopwatch starts at 00:00. Its exact inclusive domain is **00:00–39:55**, in five-second steps. Durations such as 40:00 or 00:01 are rejected, never rounded. Stopwatch stops at 39:55 without wrapping. The existing 60-Minute Timer retains its ten-second resolution and 59:50 bound.

Both timers share the monotonic clock and physical playback framework. Countdown rounds partial intervals up; Stopwatch rounds completed intervals down. Pause preserves fractions, reset restores the configured duration (or zero in Stopwatch), and timer speed is independent of rotation speed. The inherited timer rotation default is a preferred 250 ms per HTM move; Counter retains 100 ms. The shared predictive scheduler prepares the next physical target and starts before its five-second deadline. The final legal turn is timed to finish at that boundary; the control panel separately shows live one-second time. It reserves at most half the interval, including render/wake allowances, and speeds up a slower preference when needed without slowing an already faster setting. An infeasible budget or a missed deadline is reported explicitly; browser/OS scheduling cannot guarantee punctual completion on every device. Slow rendering or accelerated time can make the physical cube lag. The synchronization indicator distinguishes logical time from the displayed physical state; playback finishes one active sequence and keeps only the latest requested target.

## Verified Research dependency

[The source pin](../five-second-source.json) identifies the exact commit and file hashes on `research/cube-display-feasibility`. That branch retains the proofs, search inputs/results, independent proof review and animation benchmarks. See its [maximum-range and optimization report](https://github.com/wstein/cubistry/blob/a768d810b483837a171d9cf8f94c3cc5c8ed868c/research/five-second-timer/README.md).

Run `npm run setup` for a fresh checkout. `npm run prepare:five-second` fetches only the pinned commit when verified cached files are absent, validates every selected SHA-256, and materializes ignored `.five-second-research/` evidence plus `public/five-second-timer.v1.json`. Dev, test, typecheck and build prepare this dependency automatically. A first preparation requires GitHub network access; an intact cache works offline. No Research history is merged into the feature branch. Consecutive steps use certified move words; nonadjacent requests and catch-up use the shared physical solver to reach the pinned full states. Glyph substitution never constructs the timer display.

The selected certificate covers 480 inclusive states / 479 edges, totaling 2,237 HTM, maximum 6 and mean 4.6701. A 30-minute countdown visits 361 states / 360 edges and commits 1,681 HTM. Initial configuration is excluded from those counts. The exact range is proven maximal under the documented fixed-print/upright model; global layout/traversal move optimality remains **UNKNOWN**. Local real-animation observations, including the [endpoint timing samples](https://github.com/wstein/cubistry/blob/abcef2375a93f26b3c949929d932acabaef659b6/research/five-second-timer/endpoint-timing/README.md) for the current scheduler source, establish a sample budget, not a guarantee for all devices.

## Validation

```sh
npm run check
npm run test:e2e
```

`check` validates types, existing Counter/ten-second Timer regressions, production build, immutable Research certificates, corruption controls, full-range clock snapshots/deadlines, prepared-target bounds and cache integrity, and actual full-state controller traces. Browser tests exercise the full thirty-minute physical countdown, exact Stopwatch cap, invalid input, accessible responsive controls, application isolation, real six-move deadline observations at 250-ms, adaptive 2-s and 10-ms preferences, and accelerated playback with pause/resume/reset. Run checks and browser tests sequentially: Playwright clears `test-results/` at startup, including controller trace fixtures generated by Node tests.
