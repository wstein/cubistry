# Incremental delivery boundaries from current issue #21

## M1: existing PR #20 counter is the first real consumer

Inside the current Cubistry workspace, extract the already working physical
2×2 state/mechanics, immutable sticker frames and viewer seam into actual shared
local modules/packages. Do not create an external repository or move hosted
code without the separately required approval. Preserve proof paths and
independent replay as integration tests; do not rewrite the MVP from scratch.
Load validated fixed image/text assets through a versioned manifest and inject
a resolver into the viewer. Keep camera and product timer logic separate.
Use genuine ReScript-owned domain/mechanics/validation/notation/codecs and an
explicit checked JS/TypeScript interop contract; keep viewing/interaction in
TypeScript. This follows the binding PuzWerk addition to issue #21 (updated
2026-10-27T15:00:50Z), superseding the earlier TS-core hypothesis. PuzWerk is the
brand; `wstein/puzwerk` and `@puzwerk/*` remain planned/unpublished. No new Rust
project belongs in that framework; a versioned external adapter is the boundary.
Run the counter using those actual shared modules, not parallel legacy physics.
A solver facade prototype lives outside core and truthfully reports capabilities.

Acceptance: all 100 padded/unpadded targets and chained transitions still replay;
immutable IDs and physical asymmetric image frames survive JSON/load/render;
unknown asset/reference/schema failures are explicit; camera changes do not
change state hashes; browser interaction/target tests pass. No assertion that
3×3–7×7 are production-ready simply because the schema can represent them.

## M2: CubeAssembler becomes the next consumer, not the first blocker

First derive a conformance suite from its existing 2..7 geometry, assembly,
turn, notation and browser tests. Add 3×3, 4×4 and 5×5 mechanics conformance to
wave 1 independently by size; retain future 6/7 representations and regression
vectors rather than baking in a ceiling of 5. Compare CubeAssembler mesh/viewer
adaptation to the extracted Three adapter using the same frame/image scenes,
move playback, camera controls, accessibility and measured frame/memory costs.
Preserve capture, palette classification, assembly and UI features as application
services. Remove the duplicate physical/render truth only after its behavior is
covered and migration passes. Scope an explicit approval/review before actual
external project migration.

## M3: CubeLab/Rosetta integration after M2

Keep its notation dialects, facelet order, color schemes, validation diagnostics,
2×2 lookup integrity checks and teaching/device behaviors as contract fixtures.
Port or adapt code deliberately; do not replace the entire renderer or remove
features on the assumption that new shared packages cover them. Resolve AGPL/
GPL/Apache/MIT redistribution choices before source adoption into any package
with different licensing. Codec-loss and exact-frame tests are non-negotiable.

## Wave 2 and optional services

6×6/7×7 have actual implementation evidence in CubeAssembler/Cubacle/Orbit64,
but do not inherit a new framework support claim. Add distinct mechanics,
per-orbit validation, inner/wide/slice/dialect and image-frame tests, then
browser vertex/memory/frame-time and asset budgets. Even cubes have movable
center orbits; odd cubes have fixed centers and extra orbit/frame rules. Those
need capabilities and conformance, not a different fundamental state schema.
Optional solver, capture and device services follow measured demand. Rust
native/server and JVM adapters are valid evaluation paths; browser WASM exists
only after a real audited build and replay/size/runtime measurement, not because
a source language theoretically can target it.
